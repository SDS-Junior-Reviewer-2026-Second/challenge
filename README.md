# 자동차 조립 프로그램 리팩토링

271줄짜리 `Assemble` 클래스 하나를 목적이 드러나는 구조로 나눴다.
**화면에 찍히는 글자는 원본과 한 글자도 다르지 않다.**

## 구조

```
mission2
├── Assemble              실행 : 입력을 읽고 단계를 넘긴다
├── car                   비즈니스 : 자동차가 무엇으로 이루어지고 무엇이 금지되는가
│   ├── Car               끼운 부품을 자리별로 들고 있다
│   ├── AssemblyOrder     조립 순서
│   ├── CarAction         RUN, Test
│   ├── part              부품 카탈로그 (분류마다 파일 하나)
│   └── rule              조합 규칙
└── display               화면 : 무엇을 어떻게 보여 줄 것인가
    ├── Display           화면 경계 (콘솔은 구현체 하나일 뿐)
    ├── CarView           완성된 차를 문장으로
    ├── Josa              은/는, 이/가
    └── step              단계별 메뉴와 선택 처리
```

## 원본과 같은 동작이라는 증거

`LegacyParityTest` 는 원본 코드(`mission2.legacy.LegacyAssemble`, 클래스 이름만 바꾼 사본)와
리팩토링본에 **같은 입력을 주고 표준출력을 통째로 비교**한다.
정상 조립, 금지 조합, 고장난 엔진, 잘못된 입력과 뒤로가기까지 네 시나리오가 문자열 단위로 일치한다.

```
mvn test
```

## 무엇을 추가하려면 어디를 고치는가

| 추가하려는 것 | 고쳐야 하는 곳 |
| --- | --- |
| 부품 분류 (예: 타이어) | `car/part` 에 파일 하나 + `AssemblyOrder` 에 한 줄 |
| 부품 (예: 새 엔진) | 그 분류 파일에 한 줄 |
| 금지 조합 규칙 | `CombinationRules` 목록에 한 줄 |
| 고장난 부품 | `brokenPart(...)` 로 한 줄 |
| 다른 화면(GUI, 로그) | `Display` 구현체 하나 |

부품 분류를 추가하면 메뉴, 선택 확인 문구, 번호 범위 검증, 사양표가 함께 따라온다.
분류에 필요한 글자와 부품이 모두 한 파일에 모여 있기 때문이다.
